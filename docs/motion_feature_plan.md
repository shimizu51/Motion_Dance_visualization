# 動作特徴量の手法選定と段階的実装計画

本書は、Motion Dance Visualization に **動作特徴量（Motion Feature）の抽出** を導入するための調査・比較検討・
実装計画をまとめたものである。**実装コードは含まない。** 本書の合意後に Phase 0 から着手する。

## 0. 目的と制約

README「今後の展望」§2 が本件の実質的なゴールである。

> ViTPose の関節角度・角速度や AKAZE 残差から特定の関節にかかる負荷を推定し、「見た目の激しさ」だけでなく
> 「体への負荷が偏っている部位」を色や太さで強調表示できないか検討したい。

ここから導かれる制約は次の3点。

1. **説明可能性が必須要件。** 「なぜその評価になったのか」を人間が説明できなければ、指導者・本人へのフィードバックに使えない。
   したがって深層学習の埋め込み表現（Embedding）だけに寄せる構成は採用できない。
2. **既存の可視化ロジックを大きく壊さない。** extract / render の2ステージ分離と6つの不変条件（CLAUDE.md）を維持する。
3. **医学的な閾値判定はしない。** まずは「同じ関節の負荷が動画内でどれだけ増減しているか」という相対比較から始める。

### 本書の前提（合意済み）

| 論点 | 決定 |
|---|---|
| Phase 1 の優先 | **分析・検証が先**（CSV 出力・グラフ・妥当性検証）。映像への反映は Phase 2 以降 |
| extract キャッシュの v3 化と再抽出 | **許容する**（生キーポイント＋カメラ大域運動を追加） |
| ロードマップに含めるスコープ | **単眼3D化（MotionBERT）** と **音楽ビート同期** を Phase として含める |
| Embedding（ST-GCN 等） | 含めない（§3.3 に却下理由を記載） |
| 特徴量の対象 | **全 track_id を個別に** |

## 1. 現状把握

### 1.1 姿勢推定

| 項目 | 現状 |
|---|---|
| モデル | **ViTPose 2D top-down**（`usyd-community/vitpose-base-simple`） |
| キーポイント定義 | **COCO-17**（`Nose, L/R_Eye, L/R_Ear, L/R_Shoulder, L/R_Elbow, L/R_Wrist, L/R_Hip, L/R_Knee, L/R_Ankle`） |
| ボーン定義 | 19 edges。モデル config 由来で、キャッシュに保存されるため render はモデルを import しない |
| 人物検出 | RF-DETR Seg Small（person box + mask を1パスで取得） |
| フレームレート | 実測 29.97fps。**キャッシュに保存済み**（`ExtractCache.fps`） |
| フレーム間引き | **なし**。全フレームを処理する |
| 3D / キャリブレーション / 複数カメラ | **一切なし。単眼2Dのみ** |

`TrackFrame.depth_rank` / `depth_score` は名前に反して**深度ではない**。bbox 面積の EMA と足元 Y 座標から算出した
**レイヤ合成順のための序数**であり、metric な意味も動画間の一貫したスケールも持たない
（[`tracking.py`](../src/pose_viz/tracking.py) の `_update_depth`）。特徴量として使ってはならない。

### 1.2 データ形式

**⚠ CLAUDE.md の記述に誤りがある。** CLAUDE.md はキャッシュを `.npz` と書いているが（5箇所）、
実体は **gzip 圧縮した Python pickle（`.pkl.gz`）** である（[`cache.py`](../src/pose_viz/cache.py) の `ExtractCache.save`）。
README は正しい。**Phase 0 で CLAUDE.md を訂正する。**

```python
@dataclass
class ExtractCache:
    video_path, width, height, fps, frame_count, config_hash
    edges: list[tuple[int, int]]
    start: float; duration: float | None
    frames: dict[int, list[TrackFrame]]     # ← frame_idx がキー
    version: int                            # CACHE_VERSION = 2

@dataclass
class TrackFrame:
    track_id: int
    box_xyxy: (4,) f32                      # 作業解像度の絶対ピクセル
    keypoints: (17,2) f32                   # 絶対ピクセル。One-Euro 平滑化「後」の値
    keypoint_scores: (17,) f32
    mask_png: bytes | None                  # bbox クロップ → PNG エンコード
    akaze_points: (K,2) f32
    akaze_residual: (K,2) f32               # ← 保存されているが未使用
    akaze_residual_mag: (K,) f32
    akaze_point_ids: (K,) i64
    det_score, depth_rank, depth_score, occluded, recovered
```

特徴量設計に効く性質:

- **座標系は作業解像度（既定 1920 幅）の絶対ピクセル。正規化は一切されていない。**
  → カメラ距離が違えば同じ動きでも px 速度が変わる。**スケール正規化は自前で行う必要がある**（§2.2）。
- **`track_id` は dict のキーではなくフィールド。** 1トラックの時系列を取り出すには全フレーム走査が必要
  （現状 `render.py` の残像層が実際にこの走査をしている）。**`by_track()` ヘルパを追加する。**
- **欠損は「レコードが存在しない」ことで表現される。** NaN もゼロ埋めも補間もない。
  実測（`jellyous_occl.pkl.gz`, 180 フレーム, 6 トラック）では track 3 が最大 6 フレーム連続で欠落していた。
- **`min_hits=3` により全 extract の先頭2フレームは必ず空**、新規人物も3フレームの立ち上がりがある。
- **`keypoint_scores` はヒートマップのピーク値であり確率ではない。** 実測で最大 1.0787 を観測した。
  **`[0,1]` を前提としたコードを書いてはいけない。**
- `mask_png` は bbox クロップ＋PNG のみで、**縮小はしていない**（CLAUDE.md の「縮小」記述も誤り）。
- AKAZE のリセット: 欠損が `akaze_reset_gap`（既定3）を超えると特徴点追跡がリセットされ、
  復帰フレームの残差は全ゼロになる。

### 1.3 可視化ロジック

[`render.py`](../src/pose_viz/render.py) の `render_frame` は **モデルを一切 import せず**、
生フレーム・キャッシュ・パーティクル系だけを読む。合成順は以下（不変条件⑤: 骨格層が必ず最高輝度）。

| 順 | レイヤ | 合成 | 消費するデータ |
|---|---|---|---|
| L0 | depth 並べ替え | – | `depth_rank` 降順（奥→手前） |
| L1 | ゴースト層 | アルファ合成（土台） | 生フレーム＋`mask_png` |
| L2 | 残差パーティクル層 | 加算 | `ParticleSystem` の粒子軌跡＋`akaze_residual_mag` |
| L3 | 骨格残像層 | 加算 | 過去 `joint_trail_len` フレームの `keypoints` |
| L4 | 骨格層 | 加算（`base*2.0 + bloom`） | `keypoints`, `keypoint_scores`, `edges` |
| L5 | ポストプロセス | 乗算＋加算 | ビネット・グレイン |

`--debug-overlay` は L1〜L5 を全てスキップし、生フレームの上に box・ID・マスク輪郭・AKAZE 点・骨格を描く。

### 1.4 既存の特徴量計算 — 実質ゼロ

**repo 内に速度・加速度・ジャーク・関節角度・エネルギーの計算は一つも存在しない。**
動作を表すスカラーは **AKAZE 残差ノルムただ一つ** である。

```python
# akaze.py — 唯一の動作スカラー
M, inliers = cv2.estimateAffinePartial2D(prev_matched, cur_matched, method=cv2.RANSAC, ...)
predicted   = (M[:, :2] @ prev_matched.T).T + M[:, 2]   # 人物の大域相似運動
residual    = cur_matched - predicted                    # 残差ベクトル
residual_mag = np.linalg.norm(residual, axis=1)          # 残差ノルム
```

意味は **「その人物全体の剛体運動から外れた分の px/frame」**。時間正規化もスケール正規化もされていない。
これが駆動しているのは次の2つだけである。

1. **粒子の寿命** — 直近5フレーム平均を `norm_scale`(8.0) で割り、基準寿命の 1〜4 倍に伸ばす（`residual.py`）
2. **粒子の明度** — 直近値を `norm_scale` で割った 0.2〜1.5 を BGR に一様乗算（`render.py`）

**色相は完全に `track_id` の関数**（黄金比による hue 分配）であり、スカラー値による色相変調は存在しない。
`palette.py` の `hue_to_bgr` は `saturation` / `value` 引数を持つが、**どの呼び出し元も渡していない**。

### 1.5 未活用の資産（新規実装なしで使えるもの）

1. **`akaze_residual` の2次元ベクトル（向き付き）はキャッシュに保存済みだが、誰も読んでいない。**
   ノルムだけが使われている。動きの方向情報が無料で手に入る。
2. **全フレームの人物マスクがある。** → Quantity of Motion・収縮指数（Contraction Index）が
   **追加のモデル推論なしで**計算できる（§2.5）。
3. **`scipy` は既に依存に入っている。** Savitzky-Golay 微分・FFT・相関・ピーク検出がすぐ使える。新規依存は不要。
4. **`extract_hash()` は `render` / `residual` を除外している。** → **render 側の設定を追加しても既存キャッシュは無効化されない。**

### 1.6 特徴量設計を制約する既知の問題

| 問題 | 内容 | 影響 |
|---|---|---|
| **One-Euro が保存前に適用される** | `cli.py` で `pose_smoother.smooth()` の結果が `TrackFrame.keypoints` に入る。**生値は残らない** | 平滑化済み座標から微分すると速度・加速度が減衰する。**Phase 0 で生値を保存する理由** |
| **低スコア関節も無条件に平滑化される** | スコアによるゲートが無いため、スコア 0.035 の破綻関節が One-Euro の内部状態を汚染し後続フレームに漏れる | 計測は生値＋明示的なフィルタで行うべき |
| **欠損をまたいで平滑化が継続する** | トラックが6フレーム消えて復帰しても状態がリセットされず、`dt` が飛んだまま速度推定される | セグメント分割が必要 |
| **死に設定が2つある** | `pose.keypoint_score_threshold`（render は 0.3 をハードコード）、`akaze.trail_mode`（LK 版は未実装） | Phase 0 で文書化 |

| **テストが 0 件** | `tests/` も pytest 設定も無い | Phase 1 でテスト基盤を新設 |

## 2. 手法の洗い出し

### 2.1 評価軸の見直し

提示された7軸に、**第0軸として「算出可能性 — COCO-17・単眼2D・このキャッシュで実際に計算できるか」** を追加した。
候補のいくつかはこの軸で落ちるため、これを最初に置かないと比較が机上の空論になる。

最終的な評価軸: ①**算出可能性** ②解釈可能性 ③既存可視化との接続コスト ④実装工数 ⑤計算コスト
⑥学習・データ要否 ⑦ノイズ・欠損への頑健性 ⑧ダンス動作適合度

### 2.2 前処理 — 全特徴量の土台（これが最重要）

個々の特徴量より先に、**正規化の設計が指標の妥当性を決める**。

**スケール正規化（透視投影と体格差の同時吸収）**

```
torso_len(t) = ‖ midShoulder(t) − midHip(t) ‖          # 肩中点と腰中点の距離
scale(t)     = rolling_median( torso_len, 2秒窓 )       # 面外回転による瞬間的短縮を中央値で緩和
```

全ての位置・速度を `scale` で割り、単位を **body-length / s** にする。これでカメラ距離の違いと
被写体の体格差が同時に吸収される。移動中央値を使うのは、腰をひねった瞬間に torso が短く写る
（面外回転による短縮）影響を受けないため。

**カメラ運動不変性**

主指標は **root 相対（骨盤中点 = `(L_Hip + R_Hip)/2` 基準）** の関節速度とする。
これはカメラのパン・ズームに**原理的に不変**である。絶対速度（体幹の並進を含む）は
Phase 0 で保存するカメラ大域運動 `camera_affine` で補正した副次指標として出す。

```
root(t)    = ( kp[11] + kp[12] ) / 2
xy_norm(t) = ( xy(t) − root(t) ) / scale(t)            # 無次元
```

**時系列化と欠損処理**

`TrackSeries` として `track_id` ごとに密な時間軸に並べ直す。

- 短い欠損（既定 ≤5 フレーム ≒ 0.17 秒）は線形補間し、補間フラグを立てる
- 長い欠損はセグメント分割し、以降の特徴量に NaN を伝播させる
- **指標ごとに欠損率を必ず併記する**（欠損率 40% の対称性指標を信用しないため）

**微分**

Savitzky-Golay（`scipy.signal.savgol_filter`, `deriv=1,2`, `delta=1/fps`）を使う。窓幅は**秒で指定**して
フレームレート非依存にする（既定 0.25 秒、多項式次数 3）。SavGol はゼロ位相かつ周波数特性が明示的で、
「どの帯域を落としたか」を説明できる。

> **設計上の不変条件（新規）**
> **One-Euro は「見た目用」（低遅延・非対称・オンライン）、Savitzky-Golay は「計測用」（ゼロ位相・オフライン）**
> として役割を明確に分離する。描画には従来どおり平滑化済み `keypoints` を使い、計測には生値を使う。

### 2.3 運動学特徴量

| 特徴量 | 定義 | 単位 |
|---|---|---|
| 関節速さ | `speed_j = ‖ d(xy_norm_j)/dt ‖` | body-length/s |
| 関節加速度 | `accel_j = ‖ d²(xy_norm_j)/dt² ‖` | body-length/s² |
| 全身運動量 | `Σ_j w_j · speed_j`（`w_j` は体節質量比） | body-length/s |
| **SPARC**（滑らかさ） | 速度プロファイル `speed_j(t)` のフーリエ振幅スペクトル `V̂(ω)` を正規化し `[0, ω_c]` で切り、その弧長の負値<br>`SPARC = −∫₀^{ω_c} √( (1/ω_c)² + (dV̂/dω)² ) dω` | 無次元（0に近いほど滑らか） |

**ジャーク（3階微分）は採用しない。** 2D 姿勢推定の座標を3回微分するとノイズが支配的になり、
測っているのが動作なのか推定誤差なのか区別できない。同じ「滑らかさ」を測る指標として、
**SPARC（Spectral Arc Length）を採用する**。SPARC は速度プロファイルのパワースペクトルの弧長として
定義され、ノイズとサンプリングに対して dimensionless jerk より頑健であることが報告されている
（Balasubramanian et al., *Frontiers in Neurology* 2018 の比較で、被験者間・被験者内の変動係数が最小）。

### 2.4 関節角度

```
θ(A, B, C) = arccos( (A−B)·(C−B) / (‖A−B‖ ‖C−B‖) )    # 関節 B での挟角、0..π
```

| 角度 | 3点 |
|---|---|
| 肘 | 肩 – 肘 – 手首 |
| 膝 | 股 – 膝 – 足首 |
| 股関節 | 肩 – 股 – 膝 |
| 肩 | 股 – 肩 – 肘 |
| 体幹前傾 | 腰中点 → 肩中点ベクトルと鉛直軸の符号付き角度 |

角速度 `ω_j = dθ_j/dt`、角加速度 `α_j = d²θ_j/dt²` を SavGol で算出する。

**⚠ 足首角度は COCO-17 では定義不能。** 踵・爪先のキーポイントが存在しないため、足部セグメントを作れない。
実施するには姿勢推定モデルを HALPE-26 系（足部26点）に差し替える必要があり、extract 全体に波及する。
**今回は範囲外とし、§6 に「モデル差し替え条件」として記録する。**

**⚠ 2D 関節角度は面外回転で系統的に歪む。** カメラ面から外れた方向に曲がった肘は、2D 投影では実際より
浅い角度に見える。対策として **短縮率による信頼度** を併記する。

```
foreshortening_j = segment_len(t) / rolling_median(segment_len)
```

これが小さい区間（既定 < 0.6）は「面外回転が大きく 2D 角度が信用できない」としてマスクする。
根本解決は Phase 4 の 3D リフティング。

### 2.5 姿勢統計量（マスク由来の特徴量を含む）

**キャッシュ済みマスクを使うため、追加のモデル推論が一切不要。**

| 特徴量 | 定義 | 意味 |
|---|---|---|
| **Quantity of Motion (QoM)** | 連続フレームのシルエット差分面積 ÷ シルエット面積 | 「どれだけ体が動いたか」の総量。Camurri らの表情豊かなジェスチャ解析で使われる古典的指標 |
| **収縮指数 (Contraction Index)** | シルエット面積 ÷ bbox 面積 | 体が広がっている（大の字）ほど小さく、縮こまるほど大きい |
| **重心 (CoM)** | 体節質量比（Winter の人体計測表）で加重したキーポイント重心 | 真の重心の近似。COCO-17 には体節端点が足りないため関節点への質量配分で近似する |
| **重心軌跡** | CoM の速度・加速度・移動範囲 | 全身の並進運動。root 相対指標と対になる |
| **支持基底幅** | 両足首の水平距離 ÷ scale | スタンスの広さ |

### 2.6 左右対称性

| 特徴量 | 定義 |
|---|---|
| 振幅対称性 | `SI = |RMS(speed_L) − RMS(speed_R)| / (0.5·(RMS_L + RMS_R))`（Robinson の Symmetry Index） |
| 時間差（位相） | `speed_L` と `speed_R` の相互相関のピーク位置 → 左右の時間ズレ（秒） |

**⚠ ViTPose の左右反転に注意。** COCO のラベルは**解剖学的な左右**（被写体自身の左右）だが、
被写体が背を向けたとき top-down 2D 推定器が左右を取り違えるのは既知の failure mode である。
反転したまま対称性を計算すると、完全に対称な動きが非対称に見える。

**検出方法**: 腰中点→肩中点ベクトルと `R_Shoulder − L_Shoulder` の外積の符号は、被写体の向きを表す。
この符号が数フレームで反転する箇所を検出し、**反転区間を対称性指標から除外する**（または左右を入れ替える）。

### 2.7 リズム・周期性

**Phase 1（音声なし）**: 全身速さまたは QoM の信号から平均を除去し、自己相関または FFT
（`scipy.signal.welch`）で支配周期を求める。`テンポ[BPM] = 60 / 周期[s]`。

**Phase 3（音声あり）**: librosa の `beat_track` でビート時刻列を取得し、動きのオンセット
（速度の極大点）との時間ズレの分布を **リズム同期度** として特徴量化する。
現在、音声は `mux_audio` でパススルーされているだけで **Python 側に一度もデコードされていない**ため、
新規の抽出ステージが必要になる。

**⚠ 接地時間は低信頼度に降格する。** 足部キーポイントと地面基準の両方が無いため、
「足首の Y 速度の極小 かつ Y 座標が下位」という粗い代理しか作れない。主要指標にはしない。

### 2.8 関節負荷の代理指標

README のゴールに直結する合成指標。

```
load_j(t) = w₁·ω̂_j + w₂·α̂_j + w₃·rom_j + w₄·imp_j
```

- `ω̂_j`, `α̂_j` — 角速度・角加速度の絶対値を**動画内 p95** で正規化した 0〜1
- `rom_j` — 可動域の逸脱。`max(0, |θ_j − θ_mid| − band) / band`。`θ_mid` と `band` は動画内分布の中央値と IQR
- `imp_j` — 衝撃項。大きな減速が接地推定域で起きたときのみ立つ
- 出力は **動画内相対の 0〜1**

> **⚠ 用語の厳密化（必須）**
> これは **運動学的な代理指標であり、力学的な関節荷重ではない。** 真の関節負荷は逆動力学
> （体節質量・慣性モーメント・床反力）を要し、単眼2D映像からは求まらない。
> **コードのコメント・CSV のカラム名・UI 表示のすべてで「負荷の代理指標（proxy）」と明示し、
> 診断的な主張をしない。** README の「動画内での相対比較から始める」方針と一致する。

### 2.9 却下した候補（深層学習系）

### 3.2 推奨構成

> **解釈可能な運動学特徴量を単層の土台として置き、深層学習は「表現層」ではなく「計測改善層」として
> その下に敷く。**

これは当初想定の「解釈可能な特徴量の上に Motion Encoder による Embedding を重ねるハイブリッド」とは
**階層関係が逆**である。理由は以下。

- 想定されたハイブリッドは DL を**特徴表現を追加する層として上に積む**。この形だと Embedding 由来の出力は
  原理的に説明できず、必須要件と衝突する。さらに**ラベル付き学習データが無い**ため、ST-GCN 等は
  事前学習のまま使うことになり、日常動作クラスのロジットはダンスに対して意味を持たない。
- 本計画では DL を**下に敷く**。MotionBERT（Apache-2.0）を **「2D 関節角度が面外回転で歪む」という
  計測上の弱点を潰すため**にだけ使い、出力は依然として「膝の屈曲角」という説明可能な量のままにする。
  **説明可能性を一切犠牲にせず、精度だけが上がる。**

```
                 ┌─────────────────────────────────────┐
  可視化・評価    │ 関節負荷の代理指標／対称性／リズム同期度  │  ← すべて説明可能
                 ├─────────────────────────────────────┤
  解釈可能特徴量  │ 角度・角速度・速度・加速度・SPARC・QoM   │  ← Phase 1（学習不要）
                 ├─────────────────────────────────────┤
  前処理         │ スケール正規化・root相対化・欠損処理      │  ← Phase 0-1
                 ├─────────────────────────────────────┤
  計測改善層(DL) │ 単眼3Dリフティング（MotionBERT）        │  ← Phase 4（任意・出力は角度のまま）
                 └─────────────────────────────────────┘
```

### 3.3 却下した選択肢とその理由（まとめ）

1. **ST-GCN / CTR-GCN / Shift-GCN / GNN 埋め込み** — ラベル無し、事前学習ドメイン不一致、出力が説明不能で
   必須要件違反、既存の可視化文法に接続不能。得られる価値に対して代償が大きすぎる。
2. **MotionBERT を表現ベクトルとして使う** — 上と同じ理由。3D リフタとしてのみ採用する。
3. **足首角度** — COCO-17 に踵・爪先が無く定義不能。姿勢推定モデルの差し替えが必要（§6）。
4. **生ジャーク** — 2D 姿勢の3階微分はノイズが支配する。SPARC で置換。
5. **接地時間** — 足部キーポイントと地面基準が無く、粗い代理しか作れない。低信頼度扱い。
6. **madmom**（ビート追跡） — 精度は高いが保守停滞と導入の脆さ。librosa で開始する。

**実測から分かったこと（いずれも当初の想定を数値で裏づけ／修正したもの）**

1. **腕の 2D 角度は脚より大幅に信用できない。** 面外回転の信頼度が閾値を超える割合は
   肘 67%・肩 82% に対し **膝は 91%**。腕は体の前後に振られるため投影で潰れる。
   これはロードマップ Phase 4（3D リフティング）の必要性を、仮定ではなく実測で示している。
2. **Savitzky-Golay の区間端で非現実的な速度が出ていた。** セグメント分割の直後に体幹長の
   17 倍/秒（≒ 43km/h）という値が発生。端では窓を中央に取れず外挿になるためで、
   **`deriv >= 1` では端の半窓を NaN にする**よう修正した（最大値 17.1 → 14.0）。
3. **トラック全体に一度だけ適用した SPARC はトラック間で比較できない。** SPARC は本来ひとつの
   動作区間に対する指標で、160 秒の連続動作に適用すると長さと内容に依存する（-4.4〜-16.2 と発散）。
   サマリの代表値を **窓ごとの SPARC の中央値** に差し替えた。
4. **残る 0.1〜0.4% のフレームに姿勢推定由来のスパイクがある**（p99.9 ≈ 10、p50 ≈ 0.96）。
   これは 2D 姿勢のノイズ床であり除去しない。代わりにサマリへ **中央値** を追加し、
   平均との乖離で外れ値の量が見えるようにした。**頑健な統計量は中央値・p95。**
5. **動きの周期は音楽のテンポと同一視できない。** 最も長い 2 トラックが 119.7 / 103.7 BPM と
   一致せず、信頼度も 0.2〜0.54 と低い。ダンサーごとに何拍で 1 動作を作るかが違うため。

6. **マスク由来の QoM と骨格由来の body speed が独立に同じ時刻でピークを示した。** 別系統の

- **変調は足すだけで引かない。** 重みの低い関節を暗くすると「骨格レイヤーは必ず最高輝度」
  （不変条件⑤）が崩れるため、基準の線は常に元の明るさで描き、**太さと白熱コアを上に重ねる**。
- **色相は潰さない。** 色相は人物 ID を表す情報なので、負荷は彩度を抜いて白へ寄せる方向にだけ
  効かせる。グローには色相が残るので「誰か」と「どこに負荷が出ているか」を同時に読める。
- **`render.py` は特徴量パッケージを import しない。** 受け取るのは「キーポイント 17 点の 0..1
  スカラー」だけで、それが負荷か速度かを知らない。写像は `features/modulation.py` に閉じてあり、
  2ステージ分離の思想をそのまま踏襲している。
- 手首・足首には挟角が定義できない（COCO-17 に踵・爪先が無い）ため、**前腕は肘・下腿は膝の負荷を
  継承**して塗る。

**副産物として分かったこと**

- **`render.grain > 0` のとき出力は再現しない。** `_post_process` が `np.random.randn` を種を固定せず
  使っているため、同じ入力・同じコードでも毎回違うバイト列になる。回帰確認には `render.grain: 0.0`
  が要る（それ以外の経路は決定的であることを確認済み）。CLAUDE.md の落とし穴に追記した。

| 実装 | `_draw_skeleton` を**関節ごとの重み配列（任意引数）**を受け取れるよう拡張 → ボーン単位で色相・太さを変調 |

### Phase 4 — 単眼3D化（角度精度の改善）✅ 実施済み

> **実施順の変更**: Phase 3（音楽ビート同期）は音声という別系統の入力を要する独立モジュールで、
> Phase 4 は既存の関節角度の精度を上げる直接の延長にあたる。既存線上の改善を先に固めるため、
> **Phase 4 → Phase 3 の順に入れ替えた。**

**完了判定の結果**: 「面外回転区間で 2D の誤差が縮むことを定量的に示せる」— **示せた。**

正解データが無いため、**四肢の長さの一定性**を客観指標に使った。四肢の長さは解剖学的に一定なので、
その変動係数（CV）が小さいほど投影による短縮が解消されていることになる。

| 指標（`jellyous.mp4` 全尺・10 トラック） | 2D | 3D |
|---|---|---|
| 四肢長の変動係数 平均 | 0.2207 | **0.1126（−49.0%）** |
| 　前腕（面外回転が最も大きい） | 0.324 / 0.341 | **0.159 / 0.162（−51〜53%）** |
| 　大腿・下腿 | 0.140〜0.163 | **0.077〜0.083（−43〜52%）** |
| 肘の負荷を算出できたフレーム | 65〜67% | **92〜93%** |
| 肩の負荷を算出できたフレーム | 82% | **94〜95%** |
| 膝の負荷を算出できたフレーム | 91〜92% | 94〜95% |

**2D と 3D の食い違いは、2D が怪しい区間ほど大きい。** 短縮率 ≥0.9（カメラ面内）の区間では
中央値 7.2° しか違わないのに対し、短縮率 <0.6（面外回転）の区間では 29.1° と **4 倍**開く。
Phase 1 で作った短縮率（信頼度）が、独立に「どこで 3D が効くか」を言い当てていたことになる。

**目視でも明らか**: 2D 時代の角度時系列は肘が 0°〜180° を毎フレーム乱高下していたが、3D では
連続的で物理的に妥当な軌跡になった。**あの乱高下の大半は実際の動きではなく投影の産物だった。**

**設計判断**

- **深層学習を「表現層」ではなく「計測改善層」として使う**という §3.2 の方針をそのまま実装した。
  出力は依然として「膝の屈曲角」であり、説明可能性は一切犠牲になっていない。
- **キャッシュのスキーマ版は上げない。** `keypoints_3d` は既定値 `None` を持つ省略可能フィールドで、
  dataclass の既定値がクラス属性になるため古い pickle を読んでも静かに壊れない。80MB のキャッシュを
  27 分かけて再抽出させる理由が無いため、版を上げるのは既存フィールドの意味が変わるときに限る旨を
  `cache.py` に明記した。
- **窓は 5 割重ねてブレンドする。** 窓ごとに独立推論すると境界で 3D が不連続になり、そこから角度を
  微分するとスパイクが出る（Phase 1 で SavGol の端に対して行ったのと同じ配慮）。
- **モデル定義はベンダリングする。** MotionBERT は pip 配布が無く、実行時に `.py` を落として
  import すると「外部から取得したコードをその場で実行する」ことになる。Apache-2.0 が改変・再配布を
  許諾しているので、必要な 2 ファイルだけを `vendor/motionbert/` に固定し、加えた差分（import 1 行）を
  同ディレクトリの README に明記した。重みのみ実行時に HuggingFace から取得する。
- **`keypoints_3d` は H36M-17 の関節順**で、`keypoints`（COCO-17）と並びが違う。同じ添字が別の関節を
  指すため、取り違えないよう両方のドキュメントに明記した。
- **体幹の傾きは 3D 化の恩恵を受けない。** 3D の x,y は入力 2D とほぼ同じなので、画面内の符号付き傾きと
  いう定義のままにした（列の意味を 2D/3D で揃えるため）。

**性能**: 全尺 23,671 レコードの 3D 化が **87 秒**（MPS、左右反転のテスト時拡張あり）。

## 5. リスクと検証方法

### 5.1 妥当性検証の戦略（正解データが無い前提）

| # | 手法 | 内容 | 得られるもの |
|---|---|---|---|
| 1 | **合成信号テスト（最重要）** | 既知の角度・周波数・振幅で人工キーポイント列を生成し、角度・角速度・周期・SPARC が解析解と一致することを assert | **正解がある唯一の検証**。外部データ不要で回帰テストになる |
| 2 | **独立実装とのクロスチェック** | Sports2D（BSD-3、単眼2D関節角度）を同一クリップに走らせ、角度時系列の相関を見る | 実装バグの検出 |
| 3 | **物理的な既知条件** | メトロノーム／既知BPMのクリップでテンポ推定を、手数え可能な動作で周期を検証 | 時間軸の正しさ |
| 4 | **摂動テスト** | キャッシュ済みキーポイントに人工ノイズ・欠損を注入し、各特徴量の安定度を数値化 | **どの指標が信用できるかのランキング**を文書化できる |
| 5 | **人間の目視** | `--debug-overlay` に数値を出し、「ここは膝に来ている」という感覚と一致するかを確認 | 最終的な納得感 |

### 5.2 リスクと対策

| リスク | 内容 | 対策 |
|---|---|---|
| 座標ノイズ | 3階微分（ジャーク）はノイズが支配 | **SPARC で代替**。SavGol 窓を秒指定 |
| **One-Euro 汚染** | 平滑化済み座標からの微分は減衰。低スコア関節が内部状態を汚染 | **Phase 0 で生値を保存し、計測はそちらを使う** |
| カメラ運動 | パン・ズームが速度に混入 | **root 相対を主指標**に。`camera_affine` で絶対値を補正 |
| 透視投影（カメラ位置依存） | カメラに近い人ほど px 速度が大きい | **体幹長スケール正規化**（body-length/s） |
| 被写体の体格差 | 身長差がそのまま指標差になる | 同上 |
| fps 依存 | 別 fps の動画で値が変わる | **全指標を「毎秒」単位に。窓長も秒指定** |
| 面外回転 | 2D 関節角度が系統的に歪む | 短縮率から信頼度を出して低信頼区間をマスク。Phase 4 で 3D 化 |
| **L/R 反転** | COCO ラベルは解剖学的左右だが、背向き時に ViTPose が取り違える既知の failure mode | 肩ベクトルの符号の時間連続性で反転を検出し、対称性指標から除外 |
| オクルージョン | 重なりで関節が消える | `keypoint_scores` を妥当性マスクに。**指標ごとに欠損率を必ず併記** |
| スコアの誤解 | `keypoint_scores` は実測 1.08 まで出る（確率ではない） | `[0,1]` を前提としたコードを書かない |
| トラック切替 | ID が変わると特徴量が不連続になる | ID 変化点でセグメント分割（ID は再利用されないため安全） |
| 先頭2フレームの欠落 | `min_hits=3` により全 extract の先頭2フレームは必ず空 | 時系列の先頭を切り捨てる、または NaN 扱い |
| **医学的解釈** | 「関節負荷」は逆動力学なしには測れない | 用語を**「負荷の代理指標」「動画内の相対比較」**に統一。**診断的主張をしない** |

## 6. 残課題（Phase 1 で持ち越したもの）

**Sports2D とのクロスチェックは未実施。** 理由は、Sports2D が独自の姿勢推定器（RTMPose）を使うため、
差分を見ても「角度の式の違い」なのか「姿勢推定モデルの違い」なのかが切り分けられないこと。
式の正しさは合成信号テスト（既知の入力に既知の答えが出るか）のほうが精度よく検証できるため、
そちらを優先した。実施するなら **同一のキーポイント列を両方の角度計算式に通す** 形にすべきで、
その場合は Sports2D の角度定義部分だけを参照実装として使うことになる（BSD-3 なので可能）。

## 7. 未解決の論点（要確認）

1. **足部キーポイント** — 足首角度・接地時間を本格的にやるなら HALPE-26 系（足部26点）への差し替えが必要。
   extract 全体に波及するため、優先度の判断を仰ぎたい。現状は「範囲外」としている。
2. **負荷代理指標の重み `w₁..w₄`** — 客観的な決め方が存在しない。まず等重みで出し、映像と突き合わせながら
   調整する方針でよいか。
3. **正規化の基準区間** — 「動画内 p95 で正規化」は説明しやすい一方、**動画をまたいだ比較ができない**。
   将来的に「前回の練習より負荷が減った」といった比較が要るか。要るなら絶対基準の設計が別途必要。
4. **特徴量の時間解像度** — 毎フレーム値か、短窓（例 0.5 秒）の集約統計か。
   可視化は毎フレーム、分析は両方が要りそうだが、CSV のスキーマに影響する。
5. **集団レベルの特徴量** — 今回は全 track 個別としたが、群舞での「人物間の同期度（ユニゾンの揃い具合）」は
   将来的に価値がありそうか。
